## Components

### Tooling & process

- **`AGENTS.md`** — the contract every contributor (human or AI) works from: the navigation map, the command surface, and the four execution principles.
- **`docs/`** — `architecture/` (this map, reflecting the active RFCs) and `rfc/` (the decision lifecycle `proposed/` → `active/` → `superseded/`/`retired/`).
- **`tools/checks/`** — scripts that enforce the RFC/docs conventions mechanically (e.g. keeping each RFC in the folder its Status names).
- **Quality gate** — linters/formatters wired at the pre-commit, command-surface, and CI layers so violations are caught mechanically.
- **CI** (`.github/workflows/`) — the quality gate plus a secrets + dependency scan on every push/PR.

- **`src/client/errors.ts`** — the one normalised error shape (SPEC §7.1): maps an HTTP status or a network failure to seven codes, with a documented fallback.
- **`src/client/rate-limit.ts`** — the rate limiter (SPEC §7.2): a budget read from the response headers, with a reserve for expensive operations, a floor, pacing and the hold after a 429; it owns every wait, bounded at 15 s per call or by the caller's shorter bound, and refuses with `rate_limited`. Called by the HTTP core around every request. Its options and state are `#` private fields: an assignment through a cast adds a property nothing reads, so a refusal is not loosened (tested field by field, and for the `#` helpers `expire`, `below` and `left`). The instance is not frozen: `acquire` and `observe` can still be shadowed on it, by its only holder, the client.
- **`src/client/http.ts`** — the HTTP core (SPEC §7.1): the one send function. Basic auth and UA, `https` on the default port to exactly the configured host (checked at construction and on every URL), redirects not followed, each status mapped to its error code, the limiter acquired before and fed after, stderr limited to method, path template, status and duration, each attempt cut off after 10 s. On top of that one function: `requestWithRetry` (a GET is retried on 429, 5xx and network errors, at most 3 times with backoff; any other method on 429 only, so a write is never applied twice; the whole call ends within 30 s, with a limiter wait that would reach the deadline refused as `rate_limited` and an attempt in flight at it aborted as `network`; a caller's deadline, optional, can only shorten the 30 s, and one already reached sends nothing) and `paginate` (follows `Link` to the caller's cap of pages and items, every page URL through the host check; given a deadline, all its pages share it and a page it cuts or does not ask for is a failed page, not a short list; with none each page gets its own 30 s; its return value says whether a cap cut the list and how many attempts it sent). `requestWithRetry`'s result carries `attempts`, the attempts it sent: one counts when `request` handed it to `fetch`, whatever came back (one cut in flight by a deadline included), and not when it was refused first (URL, deadline, limiter); `request` keeps the results it got through `fetch` in a private `WeakSet`, so a subclass's override that answers without calling it, or returns anything but the object it returned (a copy included), counts nothing for that attempt. The host, the limiter, the key, the dispatcher and the URL helpers are `#` private members and the instance is frozen: an assignment through a cast to any of them, or to a method, throws a `TypeError`, and requests still go to the configured origin only (tested). The threat model is a tool's mistake or a cast, not hostile code in the process: the prototype is not frozen and `process.env` keeps the key. A subclass gets no instance fields of its own: the base freezes the instance in its constructor, so a public field throws, and a `#` field depends on engines still allowing a private field on a frozen object (the "nonextensible applies to private" proposal would refuse it).
- **`src/client/resources/ticket-fields.ts`** — `listTicketFields` (SPEC §7.3): one `GET /ticket_fields` through `requestWithRetry` (the caller's deadline, if any, passed on), the body checked by a zod schema that passes unknown keys through (choices as a list, a 2- or 3-level tree, status names or ids); a body in any other shape is `server` with the real status and a message that quotes nothing from it. On success `attempts` is the requests sent, retries included; a failure carries none.
- **`src/client/resources/agents.ts`, `groups.ts`** — `listAgents`, `listGroups` (SPEC §7.3): every page of `GET /agents` and `GET /groups` (100 per page, at most 10 pages) through `list-all.ts`, which hands the caller's deadline, if any, to `paginate` and checks each page with a zod schema before asking for the next (an agent's whole-number `id` and non-empty `contact.name`, a group's `id` and `name`; unknown keys passed through); a page in any other shape is `server` with its real status, a message that quotes nothing from it, and no further page asked for; a list the 10-page cap cut comes back with `truncated: true`; `attempts` counts the requests sent for all the pages, retries included.
- **`src/client/resources/tickets.ts`** — typed ticket reads (SPEC §7.1; T-023), with the parameters [`ticket-queries.md`](./ticket-queries.md) ("Parameters") lists. `listTickets`: one page of `GET /tickets` through `paginate` (one page), and `has_more` when a `Link` names the next; it sends `per_page` (100 unless given) and, field by field, only the other parameters given (`page`, `updated_since`, `order_by`, `order_type`, `include=stats`, `requester_id`, `company_id`), so no `updated_since` unless asked; every page is `cheap` unless the caller gives the optional trailing cost argument (`expensive` for `list_tickets`' `uncategorized` scan, T-027); `MAX_LIST_PAGE` (300) is the last page Freshdesk returns, not checked here; a failed page carries `attempts` too (0 when the limiter refused it unsent). `getTicket`: `GET /tickets/{id}` through `requestWithRetry`, `cheap` unless the caller gives the optional trailing cost argument (`expensive` for `triage_queue`'s view per row, T-029), a failed view carrying `attempts` like a failed page, with `include=stats` when asked (`stats` passed through unchecked: its reader checks it) and no other include (a requester's or company's data comes from T-025's contact and company reads, which drop phone, mobile and address). `listConversations`: every page of `GET /tickets/{id}/conversations` through `list-all.ts` (which now takes the path's `params`), 100 per page, at most 10 pages, `truncated` past the cap. `listConversationPage` (T-030): its first page alone (the oldest 100) through `paginate`, `has_more` when a `Link` names the next, `cheap` unless the caller gives the optional trailing cost argument (`expensive` for `find_similar_tickets`' excerpt), a failed page, a malformed one included, carrying `attempts`. A ticket needs a whole-number `id`, `status`, `priority`, `requester_id`, a string `subject` and a `custom_fields` object; a conversation a whole-number `id` and `user_id`, a string `body`, booleans `incoming` and `private`; unknown keys passed through. Values are checked before sending, whatever a cast let through (ids positive safe integers, `per_page` 1–100, `page` from 1, `order_by`, `order_type` and an include in their sets; keys it does not know are not sent): any other is `validation` with `http_status: null`, naming the parameter, and nothing is sent. A body in any other shape is `server` with the real status and a fixed message that quotes nothing from it; an HTTP failure (a 404 is `not_found`) is returned unchanged. Each success carries `attempts`, the requests sent with retries, for a tool's `api_calls_used`.
- **`src/client/resources/search.ts`** — `searchTickets` (SPEC §5, §7.1; T-024): one page of `GET /search/tickets` through `requestWithRetry`, cost class `cheap` unless the caller gives the optional trailing cost argument (`expensive` for `find_similar_tickets`, T-030), with the limits [`ticket-queries.md`](./ticket-queries.md) ("Parameters") records. The caller gives the conditions; the module puts them in double quotes and `HttpClient` percent-encodes them (`URLSearchParams`, a space as `+`). Checked before sending, whatever a cast let through: `query` a non-blank string with no double quote, at most 512 characters with its two quotes; `page` a whole number 1–10 (Freshdesk refuses 11); any other is `validation` with `http_status: null`, naming the parameter, and nothing is sent. No `include` (search refuses it). The body `{total, results}` needs a whole-number `total` from 0 (it can exceed 300) and results in `tickets.ts`'s ticket shape (now exported as `ticket`), unknown keys passed through; any other shape is `server` with the real status and a fixed message that quotes nothing from it; an HTTP failure is returned unchanged (a 400 is `validation` with Freshdesk's `errors[]`). Each success carries `attempts`, and so does a failure after the values were accepted (0 when the limiter refused it unsent; T-030). `SEARCH_PER_PAGE` (30) and `MAX_SEARCH_PAGE` (10) are the source's numbers for the tools that page it.
- **`src/client/resources/contacts.ts`, `companies.ts`** — `getContact`, `getCompany` (SPEC §7.1, §8.2; T-025): one `GET /contacts/{id}` or `GET /companies/{id}` through `requestWithRetry`, for `get_ticket`'s requester block. Each returns a fixed allow-list built field by field, not a pass-through: a contact's `name`, `email` (string or null) and `company_id` (whole number, or null when null or missing), a company's `id` and `name`; phone, mobile, address and every other key are dropped. The id is checked before sending, whatever a cast let through (a positive safe integer): any other is `validation` with `http_status: null`, naming the parameter, and nothing is sent. A body in any other shape is `server` with the real status and a fixed message that quotes nothing from it; an HTTP failure (a 404 is `not_found`) is returned unchanged. Each success carries `attempts`.
- **`src/client/resources/solutions.ts`** — knowledge-base reads (SPEC §7.1, §8.2; T-031), for T-032's tools. `listCategories`, `listFolders` (a category's), `listArticles` (a folder's): every page of `GET /solutions/categories`, `/solutions/categories/{id}/folders`, `/solutions/folders/{id}/articles` through `list-all.ts` (100 per page, at most 10 pages, `truncated` past the cap). `getArticle`: `GET /solutions/articles/{id}` through `requestWithRetry`. `searchArticles`: one `GET /search/solutions?term=` (a list of articles; no page parameter documented), the term percent-encoded by `HttpClient` (`URLSearchParams`, a space as `+`). Shapes are Freshdesk's documented ones, not measured. Each returns a fixed allow-list built field by field: a category or folder `{id, name}`, a listed article or search hit `{id, title, status}`, a viewed article `{id, title, text, status}` with `text` the plain `description_text` (the HTML `description` dropped). Checked before sending, whatever a cast let through: ids positive safe integers, the term a non-blank string of at most 512 characters (`MAX_TERM_LENGTH`, not a documented limit); any other is `validation` with `http_status: null`, naming the parameter, and nothing is sent. A body in any other shape is `server` with the real status and a fixed message that quotes nothing from it; an HTTP failure (a 404 is `not_found`) is returned unchanged. Each success carries `attempts`; so does a `getArticle` or `searchArticles` failure after its values were accepted. Every request `cheap`.
- **`src/schema/input.ts`** — `ticketInput` (SPEC §7.3): a tool's `{field: value}` turned into a Freshdesk API v2 ticket body (default fields under their ticket key, custom ones under `custom_fields`). A field by its exact API name or its label (trimmed, NFC, any case); a key naming two fields (shared label, or one's API name and another's label) is refused. A dropdown, ticket-type, status, priority or source value by its name (exact, else the one choice that folds alike; a name two ids share refused) or, for the last three, an id they have; a nested field as an `A > B > C` path checked level by level, levels not given sent as `null`; a field of any other type with a list of choices checked against it, with choices of another shape refused, with none passed through (agent, group, requester ids, text). Unknown, ambiguous or repeated fields, two keys landing on one ticket key and invalid choices all come back in one `validation` error (`http_status: null`), one `errors[]` entry per input key, an invalid choice listing the valid ones at the failing level, all clipped to the `errors.ts` caps.
- **`src/schema/index.ts`, `output.ts`** — the schema service (SPEC §7.3): `SchemaService.get()` loads the ticket fields, then agents and groups as id → name maps (an agent's id and name only; a list's `truncated` kept), once per TTL given by the caller (`limits.schema_ttl_s`, through `src/tools/context.ts`; a clock gone back counts as expired), shared by concurrent callers and frozen, the two name maps as a `FrozenMap` that has no method to change it (class and prototype frozen); a failed load is returned and not cached. The cache, the load in flight and the TTL are `#` private fields and the service is frozen: an assignment through a cast throws a `TypeError` and changes neither what `get()` returns nor when it loads (tested). One load ends within 30 s, its three lists under one deadline: at it the request in flight is cut and no other is started, and the error is the client's (`network`, retryable; `rate_limited` for a limiter wait that would reach it). A loaded result carries `attempts`: the requests that load sent, retries included (the three lists' `attempts` added up), for the call that started the load, and 0 for a call served from the cache or joining a load in flight, so a load is counted once; a failed load reports none (T-056). Every result handed out is frozen (a failed one with its error), so the call that started a load cannot swap what the calls that joined it get. A load started by `get_ticket_schema` (which has no `api_calls_used`), by a `get_ticket` call that then fails, or a load that fails, is reported by no call's `api_calls_used`; the limiter still sees every request. `ticketOutput` turns a raw ticket into `{label: value}`: status, priority, source, agent and group as names (the rule picked by the field's `type`), a nested field as one `A > B > C` path, an unresolvable id named rather than guessed (and an id missing from a truncated list said to be not loaded), fields hidden by the team config (label, API name or ticket key, trimmed, NFC, any case) left out; requester, company and product as raw ids.
- **`src/tools/context.ts`** — `createContext(config, dispatcher)` (SPEC §7.3, §10): the one place a `Config` becomes what the tools work with: the HTTP client, on a rate limiter it alone holds, built from the team `limits` (domain, key and override from the config, the dispatcher from the caller), the schema service with `limits.schema_ttl_s` as its TTL, the team settings as its own deep-frozen copy, and `ticketOutput` with the team `fields` already given. The context holds `http`, `schema`, `team` and `ticketOutput`, not the limiter: a tool meets the limits only through `http`, as `rate_limited`. The context object, the client and the schema service are frozen and have no own properties; this guards against a tool's mistake or a cast, not against hostile code in the process. Not covered: `context.http.constructor` and `context.schema.constructor` reach the classes, from which a tool could build its own client or service, and the lint block below does not refuse it. A tool takes the context, never the config: in `src/tools/**` (this file exempt) the eslint blocks allow, as the source of an import or re-export, exactly the entries of `eslint.tool-imports.json` for the file's place (that file is the list and names the places), its `type` entries as types only, and refuse everything else, a source with whitespace at either end, and any dynamic `import()`; in all of `src/tools/**`, this file included, they also refuse the global `process` (so `process.env`, which holds the API key, and `process.getBuiltinModule`), `globalThis.process`, `global.process`, eval, `new Function` and implied eval (proven by `test/lint-rules.test.ts`); adding a module is one reviewed line in that file. Not refused by lint: a global `require`, if a build ever exposed one (`createRequire` from `node:module` is not listed, so it is refused as an import); a re-export through a module outside src/tools/; a symlink under `src/tools/` or under a listed path; `.constructor` on the client or the schema service (above), or on any function, which reaches `Function`; a computed property on `globalThis`; the context has no `apiKey`, and the key cannot be read or printed from the context (the Authorization header and the dispatcher are private fields of the client, the client a private field of the schema service; `JSON.stringify` and `util.inspect` of the context show neither the key nor its base64 form, tested). Throws `ConfigError` for a domain the client refuses.
- **`src/tools/format.ts`** — untrusted content (SPEC §7.4): `untrusted` puts customer-written text in one `<ticket_content>…</ticket_content>` block (an array or object as its JSON; `null`, numbers and booleans unchanged), with every `<` inside the block, and every entity spelling of it (`&lt`, `&#60`, `&#x3c`, any case, leading zeros, with or without `;`), turned into `‹`, so no delimiter can form whatever invisible character or look-alike letter sits inside the word (a look-alike of `<` itself, such as `＜`, is left as written: it is not the delimiter; in JSON a `<` is written `\u003c` instead, so a `<` parses back the same); `bodyText` takes `body_text` / `description_text` when it is a string, else the HTML converted by `htmlToText` (no parser dependency: comments, script and style dropped, tags removed, entities decoded once, then the same replacement); text over its cap is cut on a code point, with a marker after the block, outside it, giving the count and the caller's way to fetch the rest; `plainName` strips tags from admin-set text (agent and group names, labels, choice names, titles), replaces `<` and its entities the same way and caps it, unwrapped; `fieldValue` wraps a ticket field's value unless its type is a known closed one and the value fits it (number, boolean, ISO date, a choice found in the field's own choices or tree); a status, priority, source, agent or group value goes through `plainName` only as a string or a number. Every pass is linear in the text's length. Applied by the tools that return such text (T-020 onwards); `ticketOutput` itself does not wrap.
- **`src/tools/list.ts`** — list envelope and cursor (SPEC §8.4): `listEnvelope(call, page)` gives `{items, next_cursor?, has_more, truncated?, api_calls_used}`, `has_more` and `next_cursor` together exactly when the tool gives a `next` position, `truncated: true` only when a cap cut the source. A cursor is `<position>.<digest>`: a whole number and an unkeyed SHA-256 (`node:crypto`, base64url) over the tool name, every argument of the call but `cursor` (the raw JSON arguments; any other value, such as a Date, a Map, NaN or a BigInt, throws a `TypeError`), keys sorted, and the position. `readCursor(call, maxPosition)` runs before any request: a cursor that is not a string, over 64 characters, not of that form, or whose digest does not match this call (another tool, an argument changed, an edited position or digest), or whose position is above the bound the tool passes (required; a missing or invalid bound throws a `TypeError`), is `validation` with `http_status: null`, its message not quoting the cursor; otherwise it returns the position only (0 without a cursor), so no cursor content reaches a URL, host or path. Unkeyed: it catches misuse and edits, not a forged cursor, which can only carry a whole number. Used by the list tools (T-021 onwards).
- **`src/tools/rows.ts`** — ticket rows (SPEC §8.4), built on the context's `ticketOutput` one field at a time: `ticketRow(ctx, schema, ticket)` gives `{id, subject, status, priority, category, updated, agent, group}`, the subject cut to 120 code points inside `<ticket_content>` (the marker after the block), status, priority, agent and group as names through `fieldValue` (HTML stripped, capped, not wrapped; an id missing from a truncated list said to be not loaded), `category` reusing the uncategorised definition (SPEC §10, so the ticket queries read the same setting the same way): `{label: value}` for the fields the team's `uncategorised_fields` names (a nested field's level selects that nested field, shown as its path), else the first nested field (label through `plainName`, a validated choice path plain, any other value wrapped), `updated` a UTC ISO 8601 instant (zone `Z` or `±HH:MM` only) or `null`; a field the schema lacks or the team hides leaves its key out (status, priority, agent, group, each category field), while the subject is always shown (`hidden` is not guaranteed in rows, SPEC §7.3). `isoUpdated`, exported, is that date rule, shared with `get_ticket`'s conversations. `ticketDetail` gives `{id, updated, fields}`: every field `ticketOutput` gives, each value through `fieldValue` by its own type, the description as text, wrapped; a caller's optional `CutOptions` cut every wrapped value (`list_tickets`' `detail: true`). In `category` and `fields` a key is the cleaned label; a used one keys the later field `Label (api_name)`, then `(2)`, `(3)`, ... if that is taken too, so no value is dropped. Used by `get_ticket` and the list tools (T-026 onwards).
- **`src/tools/ticket-query.ts`** — ticket filters (SPEC §8.2, §10; T-043), per [`ticket-queries.md`](./ticket-queries.md). `resolveFilter(schema, kind, value)`: status, priority, type, group or agent by name (trimmed, NFC, any case) or id; status and priority through their field's choices, type to Freshdesk's spelling of its choice, agent and group through the schema's name maps. A name several ids share is refused listing the ids, an unknown one lists the valid names (through `plainName`, clipped), an agent or group name missing from a truncated list says the list is incomplete; an id resolves to itself when known, or when the list is truncated. `buildTicketQuery(ctx, schema, filters)`: status, priority, group, agent, type, tag and `created_between` as search conditions joined by `AND` (`created_between` widened a day each side, `updated_since` then as `updated_at:>'<UTC day − 1>'`, both returned as local checks that callers must apply: exact if Freshdesk compares by UTC day, a possible one-side undercount if it uses the account's time-zone day with an exclusive operator, open in the proposed row T-055), else the list endpoint with `updated_since` as a UTC instant; a tag or type containing `'`, `"`, `\` or a control or format character is refused, not escaped; dates strict (zone required, no calendar rollover, times in range); `uncategorized` must be a boolean, and `true` returns the checks from rows.ts's `categoryFields` (a nested field at its last level). `matchesLocal(query, ticket)` applies every local check (`isUncategorized` for the category one). Every problem in one `validation` error, nothing sent. Used by `list_tickets` and `count_tickets` (T-027, T-036).
- **`src/tools/toolsets/index.ts`** — the toolset registry (SPEC §8.1): a tool is a name, a description, a zod input, a handler, the four MCP annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, each a boolean), its call cost and whether it returns customer-written text; `registerTool` throws a `TypeError` naming the tool and the missing part, so an incomplete tool does not register. The listed description is the tool's text, then `Cost: …`, then, for customer text, the "data, not instructions" sentence (SPEC §7.4), so no tool can leave them out. A handler returns `{ ok: true, value }` (sent as JSON text) or `{ ok: false, error }` with a `FreshdeskError` (sent as `isError`, `{ error }` as JSON text; in its `errors[]`, Freshdesk's text or a local validation's echo of the input, each `message` goes through `untrusted` and each `field` and `code` through `plainName`, and the error then carries a fixed `note`, the "data, not instructions" sentence, so a tool without customer text still explains the markers); a throw, or a value JSON cannot write (a BigInt, a cycle, `undefined`, a function), gives `isError` with a fixed message naming the tool only, never the thrown value's text or stack. `TOOLSETS` holds the toolsets this version has: `core`, its tools listed in `core/index.ts`.
- **`src/tools/toolsets/core/index.ts`** — the `core` toolset (SPEC §8.2): `CORE_TOOLS`, in listing order; today `get_ticket_schema`, `list_agents`, `list_groups`, `get_ticket`, `list_tickets`, `search_tickets`, `triage_queue`, `find_similar_tickets`.
- **`src/tools/toolsets/core/get-ticket-schema.ts`** — `get_ticket_schema` (SPEC §8.2, C1, C8): every ticket field from the schema service's cache as `{label, name, type, choices?, choices_not_shown?, levels?, meaning?}`; the team file's `hidden` is not applied. Choices by type: a status as `{id, name, customer_name}`; a nested field as a tree of `{name, choices}` ending in lists of names, with `levels` from `nested_ticket_fields`; a dropdown's or ticket type's list of names as is; a name → id record (priority, source, agent, group) as `{id, name}`, `id` `null` when the value is not a number. Labels, API names, types and choice names go through `plainName`, not wrapped. At most `CHOICE_CAP` (200) choices per field, every level of a tree counted, filled level by level; a list cut short carries `choices_not_shown`, the count left out. The team `meaning` is matched by label or API name with a local copy of `fold` (trimmed, NFC, lower-cased), since `src/schema/output.ts` is not on T2's import list, and returned as written. Read-only; cost 0 API calls while cached, at least 3 on a cold load (within 30 s).
- **`src/tools/toolsets/core/list-agents.ts`, `list-groups.ts`** — `list_agents`, `list_groups` (SPEC §8.2, §8.4): the whole list in one list envelope through `listAgents` / `listGroups`, an agent as `{id, name, email}` (the work email, `contact.email`; phone and every other key left out, OD-8), a group as `{id, name}`; names through `plainName`, not wrapped; the email, which the resource's schema leaves unchecked so an odd one cannot fail the schema service's load, through `plainName` capped at 254 when it is a string, else `null`; `truncated: true` when the 10-page cap cut the list; one 30 s deadline per call shared by all its pages; `api_calls_used` is every request sent for the list, retries included (`listAll`'s `attempts`), as the description and cost say. Each reads its cursor first with `MAX_POSITION = 0` (it never gives a `next_cursor`): a cursor from another call or past 0 is `validation` with nothing sent. Input `{cursor?}`, no zod `default` or `transform`.
- **`src/tools/toolsets/core/get-ticket.ts`** — `get_ticket` (SPEC §8.2, §7.4, §8.4, C3; T-026): one ticket as `{ticket, requester?, recent_tickets?}` beside a list envelope whose `items` are its conversations. The cursor is read first with `MAX_POSITION` (`THREAD_CAP / THREAD_PAGE - 1`, 99): one from another call or past it is `validation` with nothing sent. Every call then takes the schema (no request while cached), a cursor call too: it says whether the team hides the requester. Without a cursor: `getTicket` (no include), then `ticket` through rows.ts's `ticketDetail` (the tool neither extends `ticketOutput` nor maps fields itself: each value goes through `fieldValue` with its own `TicketField`, each key through `plainName`, a `custom_fields` key no field names is never read); `requester` as `{id, name, email, company}` from `getContact` and `getCompany`, the name and the company name through `plainName` then inside `<ticket_content>`, the email as written only in a plain shape (one `@`, ASCII letters, digits and `._%+-`, at most 254 characters) and inside `<ticket_content>` otherwise; `company` is the contact's company, not the ticket's `company_id`, and `null` with no request when the contact has none; with `include_recent: true`, `recent_tickets`: the requester's last `RECENT_COUNT` (10) tickets by creation, this one left out, as `ticketRow`s, by the request [`ticket-queries.md`](./ticket-queries.md) names (`requester_id`, `order_by=created_at`, `order_type=desc`, `per_page=11`, no window), a row with another `requester_id` dropped. The thread is read whole on every call through `listConversations` and cut locally into pages of `THREAD_PAGE` (10), oldest first; a call with a cursor returns the envelope only. A conversation is `{id, created_at, user_id, incoming, private, source, from, to, cc, attachments, body}`: `created_at` through rows.ts's `isoUpdated` (a UTC instant or `null`, as a ticket's `updated`), `source` Freshdesk's number as sent (not mapped to a name), `from`, each of `to` and `cc` and each attachment's name each inside its own `<ticket_content>` (cut at 300), the body as text inside `<ticket_content>`, cut at `BODY_CAP` (4,000 code points) with the marker, which names no way to fetch the rest (parked); the description keeps `TEXT_CAP`. `truncated: true` past 1,000 conversations. Hidden (SPEC §8.4): a team that hides the requester field gets no `requester` key and no contact request, `user_id: null` on every conversation (whatever its `incoming`), no `from`, `to` or `cc`, and `recent_tickets_unavailable: "requester hidden"` in place of `recent_tickets` with no request; one that hides the company field, no `company` key and no company request. The check fails closed: with the field missing from the schema, a hidden team key folding to `requester` / `requester_id` (`company` / `company_id`) still hides it. Not covered: a body, a subject or an attachment name that itself names the requester; and, when the schema lacks the field, a team key that is the field's localised label rather than one of those names. One 30 s deadline per call shared by every request. A failed ticket or thread read is returned as is (an unknown id is `not_found`); a failed contact, company or recent-tickets read keeps its code under a fixed message naming the part ("The ticket was read; its requester's contact could not be read (HTTP 404)."), without `errors[]`. `api_calls_used` is every request the call sent, retries included, the schema's load too when this call started it (the schema service's `attempts`; T-056). Input `{ticket_id, include_recent?, cursor?}`, no zod `default` or `transform`.
- **`src/tools/toolsets/core/list-tickets.ts`** — `list_tickets` (SPEC §8.2, §8.4, C1; T-027): the nine filters through `buildTicketQuery`, rows through `ticketRow` (or `ticketDetail` with `detail: true`, each wrapped value cut at `DETAIL_VALUE_CAP`, 1,000 code points, the marker saying `get_ticket` returns more of the text) in the list envelope; `matchesLocal` is applied to every ticket either endpoint returns. A cursor position is a page of the source, and the source is known from the arguments alone (`SEARCH_FILTERS`: status, priority, group, agent, type, tag, `created_between`), so the cursor is read before any request with search.ts's `MAX_SEARCH_POSITION` (`MAX_SEARCH_PAGE - 1`, 9) or `MAX_LIST_POSITION` (`MAX_LIST_PAGE - 1`, 299); a built query naming the other source throws (the registry's fixed internal error). Search: one page of 30 a call, more while `total` reaches past the page and the page is not the tenth; `total` over 300 is `truncated: true` on every page (with a date filter that is the widened set's count). List endpoint: one page of `LIST_ROWS` (30) a call, more while Freshdesk links a next page; a page 300 that still links one, or comes back full, is `truncated: true` (reach 9,000 tickets). With `uncategorized` and no search filter the call is a scan: pages of `SCAN_PER_PAGE` (100; `DETAIL_SCAN_PER_PAGE`, 30, with `detail: true`), each sent as `expensive` (refused below the reserve, paced), until the list ends, `LIST_ROWS` rows are kept, `SCAN_PAGES` (10) pages are read or `SCAN_START_MS` (15 s) of the call have passed; the next call resumes at the next list page. `has_more` and `next_cursor` come from the source, never from the rows left after the local checks: a call can return fewer rows than a page, or none, with `has_more: true`, and a scan up to `SCAN_MAX_ROWS` (129; `DETAIL_SCAN_MAX_ROWS`, 59, with `detail: true`). A failed request fails the call, except that a scan with at least one page read whose later page the limiter refuses (`rate_limited`, no HTTP status) returns the rows kept so far with `next_cursor` at that page; a limiter wait that would reach the deadline is refused that way too, so near the 30 s mark a later page takes this branch, and only an attempt cut in flight (`network`) or Freshdesk's own refusal (a 403) fails the call. One 30 s deadline per call; `api_calls_used` is every request sent, retries included, and the schema's load when this call started it. Input `{status?, priority?, group?, agent?, type?, tag?, uncategorized?, updated_since?, created_between?, detail?, cursor?}`, no zod `default` or `transform`.
- **`src/tools/toolsets/core/search-tickets.ts`** — `search_tickets` (SPEC §8.2, §5; T-028): Freshdesk's ticket query language passed through, rows through `ticketRow` in the list envelope. Input `{query, cursor?}`, no zod `default` or `transform`. The query reaches `searchTickets` as written: nothing is parsed, trimmed or rewritten and no rule looks for a field the team hides (owner, 2026-11-23; the rows still leave a hidden field out). The cursor is read first, before any request, with search.ts's `MAX_SEARCH_POSITION` (`MAX_SEARCH_PAGE - 1`, 9): a position is a search page, and one from another call or past the bound is `validation` with nothing sent. Then the schema (no request while cached), then one page of 30: `has_more` and `next_cursor` from search's `total` alone (more while `total` reaches past the page and the page is not the tenth), `total` over 300 `truncated: true` on every page. A query the client refuses (blank, containing `"` or `\`, over 510 characters) is `validation` naming `query`, never its text, with no search request (on a schema not yet cached its load has been sent); Freshdesk's 400 (a field that is not searchable: a nested (dependent) field, at any level, is not) is returned with its `errors[]`, which the registry wraps. The description names the first-300 cap, "no full text" and how the query is written (single quotes, no `"` or `\`). One 30 s deadline per call (`CALL_DEADLINE_MS`); `api_calls_used` is every request sent, retries included, and the schema's load when this call started it.
- **`src/tools/toolsets/core/triage-queue.ts`** — `triage_queue` (SPEC §8.2, §8.4, C2; T-029), per [`ticket-queries.md`](./ticket-queries.md): the tickets in status 2 or 3 from search (`status:2 OR status:3`), any other status dropped locally, no ranking. Input `{reply_signals?, cursor?}`, no zod `default` or `transform`. The cursor is read first, before any request, with search.ts's `MAX_SEARCH_POSITION` (9): a position is a search page. One page of 30 a call; `has_more` and `next_cursor` from search's `total` alone, `total` over 300 `truncated: true` on every page. A row is `ticketRow` plus `created`, `age`, `first_response_due`, `resolution_due` (`fr_due_by`, `due_by`), `first_response_overdue`, `resolution_overdue` (the due time has passed at the call's start, whether or not a response was sent; `reply_signals` refines the first) and `first_response_escalated`, `resolution_escalated`, `next_response_escalated` (`fr_escalated`, `is_escalated`, `nr_escalated`); dates are UTC ISO 8601 instants through `isoUpdated`, durations in words (the two largest units of days, hours and minutes, rounded down; `under a minute`); a value missing or not in its expected form is `null`, unknown, never a guess (a date without a zone, a flag that is not a boolean, a time in the future for a duration). `reply_signals: true` adds `last_customer_reply`, `since_last_customer_reply` and `unanswered_customer_reply` from `stats.requester_responded_at` and `stats.agent_responded_at`: one `getTicket(…, ["stats"])` per returned row, one after another, each `expensive` (refused below the reserve, paced), so at most 31 requests a call (about 61 credits), retries apart; without it no ticket is viewed and the rows have no reply key. `stats` is read key by key: a key absent or neither `null` nor an ISO 8601 date-time with a zone makes the signals that need it `null`. With no later customer reply (`requester_responded_at` `null`) the last message is the opening one, so `last_customer_reply` is `created`; `unanswered_customer_reply` is true when `agent_responded_at` is `null` or earlier than the customer's message. With the flag `first_response_overdue` is true only when the due time has passed and `stats.first_responded_at` is `null`, and `null` when the due time has passed and that key is unreadable or the ticket was not viewed. A view answered `not_found` leaves the row unviewed (the three reply signals `null`). Once a view was answered, a later one the limiter refuses unsent (`rate_limited`, no HTTP status) ends the views: every row of the page is returned, the rest unviewed, with `reply_signals_incomplete: true` beside the envelope and `api_calls_used` the requests sent; any other failed view, and a refusal of the first, fails the call. Order: a page's rows by resolution due time, earliest first, none last, ties by id; the pages follow search's order, so it holds within a page only (said in the description). One 30 s deadline per call, ages measured at its start; `api_calls_used` is every request sent, retries included, and the schema's load when this call started it.
- **`src/tools/toolsets/core/find-similar-tickets.ts`** — `find_similar_tickets` (SPEC §8.2, C3; T-030), per [`ticket-queries.md`](./ticket-queries.md): best-effort past cases like one ticket, no full text. Input `{ticket_id, days?, cursor?}` (`days` 1–365, 90 when absent, applied in the handler), no zod `default` or `transform`. The cursor is read first with `MAX_POSITION` 0 (one page only: has_more always false). Then, one after another and each `expensive` (refused below the reserve, paced): `getTicket` (first, so below the reserve nothing is sent), the schema, one `listTickets` page of 100 for the ticket's `requester_id` and one for its `company_id` (none without one), each with `updated_since` N days ago, one `searchTickets` page of `(status:4 OR status:5) AND updated_at:>'<day>'` (the UTC day of N days ago less one; not sent when the ticket has no category to match), and one `listConversationPage` per result: at most `CALL_BOUND` (9) requests, retries apart, plus the schema's load when not cached. A candidate is any ticket returned, once, other than the ticket itself, in status 4 or 5, `updated_at` at or after N days ago (`matchesLocal`), sharing the category (rows.ts's `categoryFields`; every category field equal to the ticket's, each level of a nested one; an empty one on the ticket shares nothing), the requester or the company. Order: shared subject keywords, most first, then `updated_at` latest first, then id highest first; `RESULTS` (5) returned. Keywords: the subject lower-cased, NFC, runs of `\p{L}\p{M}\p{N}`, at least 3 code points, a short English and Italian stop-word list and `fwd` left out, each once. Hidden, by get-ticket.ts's exported `shows` (fails closed): a hidden requester (company) gets no requester (company) list and never `same: "requester"` (`"company"`); a hidden category field is still compared and reported (SPEC §7.3, not guaranteed). An item is `ticketRow` plus `same` (`category`, `requester`, `company`), `shared_keywords` and `excerpt`: the last public agent reply (`incoming: false`, `private: false`; never a private note) of the first conversations page as text, wrapped, cut at `EXCERPT_CAP` (500) with the marker; `null` with none or on a `not_found`. `truncated: true` when a list linked a next page or the search `total` passed its page. A failed request fails the call, except that after the view, a request the limiter refuses unsent (`rate_limited`, no HTTP status) ends the reads: what was read is ranked and returned, the excerpts not read `null`, with `incomplete: true`. One 30 s deadline; `api_calls_used` every request sent, retries included, and the schema's load when this call started it.
