Close the current task and prepare the next session. Follow these steps in order.

1. Run `make quality`. If anything is red, do NOT proceed to step 3: tell the owner what is red and ask whether to fix it now or record it. A recorded red state must be described precisely in HANDOFF.md under "Known red".
2. Review the diff since the task started with three sub-agents, dispatched in one message so they run in parallel, each given the explicit range `<base>..HEAD` (base: the commit the task started from) and the path of a diff file the main session first makes with `mktemp`, outside the worktree, headed by four parts, a base line, a HEAD line, the `--stat` block and the line `paths added or changed in the range:` with every path any commit of the range added or changed under it, then the full diff, the current task file as it stood at base (`<task file>`, its path from the repository root) under one line `task file at <base>: <path>`, or the single line `task file absent at base`, which exempts nothing, and one trailer line, `end of diff: <HEAD> <nonce>`, the nonce drawn when the file is written: `f=$(mktemp) && b=$(git rev-parse <base>) && h=$(git rev-parse HEAD) && n=$(od -An -N4 -tx4 /dev/urandom | tr -d ' ') && [ -n "$n" ] && { echo "base: $b" && echo "HEAD: $h" && git -c core.quotePath=false diff --no-renames --text --no-textconv --no-ext-diff --no-color --no-relative --stat=1000,999 "$b..$h" && echo "paths added or changed in the range:" && git -c core.quotePath=false log --no-renames --text --no-textconv --no-ext-diff --no-color --no-relative --diff-merges=first-parent --root --no-show-signature --diff-filter=d --name-only --format= "$b..$h" && echo && git -c core.quotePath=false diff --no-renames --text --no-textconv --no-ext-diff --no-color --no-relative "$b..$h" && echo && (t=$(git show "$b:<task file>" 2>/dev/null) && printf 'task file at %s: %s\n%s\n' "$b" "<task file>" "$t" || echo "task file absent at base") && echo "end of diff: $h $n"; } > "$f"; echo "$f"; tail -n 1 "$f"`. It prints the file's path and its last line; a last line that is not the trailer means a command failed: fix it and write the file again before dispatching. Base and HEAD are resolved once; `--no-renames` lists and shows a renamed file as a delete and an add; `,999` keeps every path whole whatever the user's `diff.statNameWidth`; `git log --diff-filter=d` names every path a commit of the range added or changed, a merge's changes against its first parent and a root commit's included, so a file added and deleted, or overwritten and reverted, inside the range is still listed, and `--no-show-signature` keeps signature lines out of the list; `-c core.quotePath=false` writes a non-ASCII path as it is, not quoted; `--text --no-textconv --no-ext-diff --no-color --no-relative` keep the diff git's plain text whatever the project's attributes or config; `&&` leaves a failed diff or `git log` without a trailer, and `[ -n "$n" ]` leaves the file `mktemp` made empty on an empty nonce, so no trailer either; and a failed `git show` falls back to `task file absent at base`, so the trailer is still written. The nonce never goes in a dispatch message. The three are `code-reviewer` (the four principles), `security-reviewer` (the security surfaces) and `compliance-reviewer` (the diff against the task file's `## Wireframes`; with `none` it says so and stops, which is a complete review). Skip a reviewer only if it already ran on this same diff in this session. The dispatch to `compliance-reviewer` names its round, "full round" or "scoped round". Each dispatch message, to all three, `code-reviewer` included, asks its reviewer to quote base, HEAD, the `--stat`'s last line and the trailer before its findings. The dispatch to `code-reviewer` says the diff file replaces `git diff`, no Bash call. Compare each reviewer's four quotes, base and HEAD with `git rev-parse` of the range it was dispatched, the `--stat`'s last line and the trailer with the file; a missing or wrong quote is "stale diff file". Resolve or explicitly dismiss each finding from each; the three together are one review round (rule 9), and the scoped round re-dispatches all three, each given the range `<R1>..HEAD` and a diff file written the same way for it, its dispatch to `compliance-reviewer` naming the "scoped round", where R1 is the HEAD the full round reviewed, so no commit between the rounds goes unreviewed. "section missing", "not checked: <item>", "task file not found", "empty diff", "diff file not readable", "diff file truncated" and "stale diff file" are not findings to dismiss: each is a red gate, like a reviewer with no output, cleared only by fixing the task file, the range or the diff file and dispatching that reviewer again. Delete the diff file after the round. HANDOFF.md's "Reviews" records R1 and both ranges, and names all three and what each reported, including a reviewer that produced no output, which is a red gate (see "Before marking a phase done").
3. Update the current task file in `docs/tasks/`:

   - "Dead ends": what was tried and abandoned, and why. Write "none" if none.
   - "Open doubts": anything uncertain that the next session or the owner should judge. Write "none" if none.
   - "Context pressure": one of `low | ok | tight | overflowed`. If `tight` or `overflowed`, add a one-line suggestion on how the task should have been split.
   - Status: `done (YYYY-MM-DD)`, or `doing (YYYY-MM-DD)` with a precise "Next action" if unfinished. The date is the day of the change, from `date +%F`; never a bare status.
4. Update `docs/tasks/PLAN.md`: the task's status, dated the same way. If the task revealed missing or mis-sized later tasks, add them as rows with status `proposed` (no task file yet) and list them in HANDOFF.md under "Proposed plan changes" for the owner to confirm at the next `/pickup` or `/decompose`. The one exception is when the current task is itself a `plan` task: then `/decompose`'s authority extends through this handoff, and edits to rows created or re-planned in this session are in scope (record them in the re-plan note).
5. Run `date -Iseconds`, then rewrite `docs/HANDOFF.md` from scratch, one page at most. Its sections, in this order: "Written" (that timestamp, exactly as printed), "Describes commit" and its "CI" (filled in step 8), "Current task" with its dated status, "Next action" (the exact first step for the next session), "Read before anything else", "Reviews", "Proposed plan changes", "Open doubts", "Dead ends", "Known red", "Checkpoint" (what `make quality` printed: counts, not "green"). An empty section says "none".
6. Append to `docs/journal.md` any learning worth keeping that is too small for an RFC, under a `## YYYY-MM-DD` heading, each entry ending with the task id. Absolute dates only. Skip if nothing.
7. If `.claude/.compacted` exists, delete it now (the handoff you just wrote supersedes the compacted context).
8. Commit everything with the task id in the message (`T-NNN: <what changed>`). Never `--no-verify`. Then `git push`: **a handoff describes a pushed commit**, not a local one. Then observe CI for that commit (`gh run list --workflow=quality.yml --commit <hash>`, `gh run watch <id>`) and record in HANDOFF.md the hash, the run URL and `green`, or `red` with the reason under "Known red".

   The commit is already pushed by then, so record it in a follow-up stamp commit (`T-NNN: stamp handoff hash and CI`) and push that too; never amend a commit that is already on the remote. `/pickup` expects HEAD to be exactly this stamp commit.

A red CI is a red `make quality`: fix it, or describe precisely what is red and why, and tell the owner. A fix is a new pushed commit: it becomes the hash HANDOFF.md describes, CI is observed again for it, and the stamp commit follows the last fix.
